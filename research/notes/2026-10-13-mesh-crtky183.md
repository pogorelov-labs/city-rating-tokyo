# Census 500m/250m mesh (e-Stat 地域メッシュ統計) for Tokyo — does it improve on 町丁目? (CRTKY-183)

Researched: **2026-10-13**, by the open-data research agent. The ticket allows a
quick reject. All network checks, downloads and computations below were run by
me in this session; commands and outputs are quoted in the appendix. Nothing
here is an implementation decision — the owner adopts or closes.

**TL;DR: recommend REJECT (close the ticket).** The mesh data is real, open,
tiny (Tokyo bbox ≈ 1.3 MB of boundaries + 2 MB of 500m CSVs, 政府標準利用規約 2.0
— same portal the repo already uses) — but it has **no consumer it improves**:

1. **The crime numerator only exists at 町丁 level.** Keishicho publishes the
   weighted-crime source at 町丁 granularity and nowhere finer/coarser-spatial;
   a mesh pipeline would have to *allocate* 町丁 crimes into mesh cells, adding
   error instead of removing it.
2. **The mesh has no daytime population.** The 2020 census mesh table T001141
   (54 columns, verified live) carries resident population/age/households only —
   `昼間` appears nowhere in the file. The pipeline's whole §2 denominator rule
   (daytime when >2× residents — `scripts/scrapers/ingest-crime-open-data.py:389-398`)
   runs on TMG table 11 昼間人口 **by 町丁**, which has no mesh counterpart.
   Replacing 町丁 would silently regress every CBD catchment (Hibiya's catchment
   has zones with 0–13 residents and ~180k daytime).
3. **The mesh is coarser than the unit we already have.** Median Tokyo 町丁
   (計 5,979 small areas) is **0.178 km²** vs a 500m cell's 0.25 km²; **74.5%**
   of 町丁 are smaller than one cell.
4. **A live numerical example on real cached data** (reproducing the pipeline
   exactly, then swapping 町丁 for 500m cells): Shinjuku 48.6 → 58.8 (+21%),
   **Hibiya 12.2 → 27.0 (+122%)**, Sugamo 21.0 → 24.6 (+17%). The mechanism is
   named in §4: cell-center catchments pull in 新橋二丁目 (897 m away, weighted
   230) while dropping Ginza 5–7-chōme and 丸の内二丁目.
5. Bangkok's grid layer is **not** a mesh consumer: `scripts/bangkok/build.py`
   builds it from OSM/Overture POIs, parks and transit rasters; its resident
   weight is a POI proxy. Tokyo has no grid level in the app and no product ask
   for one; if the owner ever adds one, mesh *could* supply the resident-weight
   plane — that hypothetical is §3c, and it is the only thing keeping this from
   being a trivial close.

## 1. What the pipeline does today (code refs)

- **Unit of rating = station.** Greater Tokyo is 1,493 stations
  (`CLAUDE.md:5,14`); there is no district or grid level for Tokyo in the app —
  the levels-of-detail switcher and the 200 m grid exist only under
  `app/src/data/bangkok/` (`bangkok/grid.json` is the only grid file in
  `app/src/data/`; `CLAUDE.md:448-451`).
- **Tokyo safety, neighborhood level** (`scripts/scrapers/ingest-crime-open-data.py`):
  - Keishicho 町丁 crime CSV is joined 1:1 to e-Stat 2020 small areas
    (`tokyo_zones`, `ingest-crime-open-data.py:453-496`; join rate 99.4%, my
    reproduction below matches);
  - each zone carries `pop` (small-area `JINKO`), `daytime` (TMG 2020 table 11
    昼間人口 by 町丁, `load_tokyo_daytime`, `:499-523`) and `weighted` (formula
    `:69-70, 385-386`);
  - **station catchment** = 町丁 zones whose representative point is ≤ 800 m
    from the station (`:602`), all-or-nothing membership, rate =
    Σweighted / denominator(Σpop, Σdaytime) (`denominator`, `:389-398` —
    daytime if >2× residents, residents if <1.5×, mean in between), clamped to
    [1/3, 3]× the municipal rate (`:607`). This is the only 町丁-weighted
    aggregation in the Tokyo pipeline.
- **Crime denominators, municipal level**: e-Stat Statistics Dashboard API for
  resident (2025) and daytime (2020 census) population per municipality
  (`POPULATION`, `:142-148`, `dashboard`, `:173-191`); written to
  `data/crime/municipal-2024.csv`.
- **compute-ratings.py is a pure consumer of the precomputed JSON** — it reads
  `data/crime/station-safety.json` (`:138-141`) and files the rate into the
  safety signal with the source's own confidence (`:426-439`). No spatial
  aggregation happens there; mesh vs 町丁 is entirely an ingest-script question.
- **Bangkok's grid** (`scripts/bangkok/build.py:904-917, 947-952`): a regular
  200 m sample grid over the 50 districts; each point scores what a resident
  can reach (POIs/parks/transit rasters); the district signal is the
  *resident-weighted* mean of points, the weight itself being a POI-density
  proxy (`0.1 + 0.9·min(1, activity/10)`) because no census grid exists for
  Thailand. Census mesh for Tokyo would map onto that *weight plane*, not onto
  any current Tokyo consumer.

## 2. e-Stat 地域メッシュ統計 — mechanics, verified live

Provision is through e-Stat 統計地理情報システム (statmap-search), exactly like
the small-area boundaries the repo already downloads
(`ingest-crime-open-data.py:124-140`). Overview page:
<https://www.stat.go.jp/data/mesh/>; 2020 census mesh released 2022-07-27
(<https://www.stat.go.jp/data/mesh/r2_w.html>); mesh types 3次(1km) / 4次(500m)
/ 5次(250m) listed on the download portal. No appId needed.

**Boundary data** — `GET https://www.e-stat.go.jp/gis/statmap-search/data?dlserveyId={H|Q|S}&code={1次メッシュ}&coordSys=1&format=shape&downloadType=5`
(verified by download; `H`=500m, `Q`=250m, `S`=1km; `code` = first-mesh code,
Tokyo bbox = 5339 + 5439):

| file | 5339 (bytes) | 5439 (bytes) | features (5339) | attributes |
|---|---:|---:|---:|---|
| 1km mesh (S) | 162,469 | 164,518 | 6,300 | `KEY_CODE`, `MESH1_ID`–`MESH3_ID`, `OBJ_ID` |
| 500m mesh (H) | 669,886 | 681,776 | 25,200 | `KEY_CODE`, `MESH1_ID`–`MESH4_ID`, `OBJ_ID` |
| 250m mesh (Q) | 2,753,194 | 2,801,863 | 100,800 | `KEY_CODE`, `MESH1_ID`–`MESH5_ID`, `OBJ_ID` |

**Statistics data** — `GET …/data?statsId=T001141&code={1次メッシュ}&downloadType=2`
(a tab-separated CSV `tblT001141H5339.txt`, cp932, inside a zip):

| file | 5339 (bytes) | rows (5339) |
|---|---:|---:|
| T001141 500m (人口・世帯, 54 cols) | 1,175,366 | 16,672 data rows |
| T001141 5439 | 897,729 | — |
| T001225 125m (same columns) | 8,669,567 | — (not inspected) |

What the CSV contains: `KEY_CODE, HTKSYORI, HTKSAKI, GASSAN` + population
(総数/男/女), age bands (0–14, 15–64, 18+, 20+, 65+, 75+, each 男/女/計),
households, 住宅の種類 … **No 昼間人口 — the string `昼間` does not occur in the
file.** Secretization is present and non-trivial: `HTKSYORI=2` rows carry `*`
with the value merged into `HTKSAKI` (sample row 533900064 → merged into
533900073). At 125m a third-party project reports ~36% of cells secretized
nationally (<https://github.com/shiwaku/japan-food-access-analysis>,
`scripts/01_fetch_mesh_population.py`).

Formats: SHP verified live; MDB (Access) is offered by the portal per its
documentation but I did not verify an MDB download (my `format=mdb` probe
returned 404 for the small-area variant; I did not chase it — SHP is what the
repo's parser reads anyway). License: 政府標準利用規約 2.0, the same terms the
repo already records for e-Stat small-area boundaries
(`ingest-crime-open-data.py:131`).

Freshness: the mesh epoch is **2020 census — the same epoch the pipeline's 町丁
denominators already use** (small-area `JINKO` from the same 2020 boundary
files + TMG 2020 daytime). No freshness gain anywhere.

## 3. The three candidate consumers

**(a) Station catchment weighting.** Today: 町丁 representative points, ≤800 m,
all-or-nothing (`ingest-crime-open-data.py:601-611`). A 500m-mesh version can
only change *membership geometry* — the crimes still come from 町丁 rows, so
they must be assigned to cells first (by containing representative point),
then the catchment is cells whose **centers** are within 800 m. That
re-anchors every zone by up to ±353 m (half the cell diagonal) — quantization
in the wrong direction, because 74.5% of Tokyo 町丁 are smaller than one cell.
A hypothetical area-overlap weighting of 町丁 straddling the 800 m line would
fix a second-order error while introducing first-order allocation error (§4).
No improvement available.

**(b) Crime denominators.** Municipal: dashboard API, fine. Tokyo
neighborhood: resident `JINKO` + TMG 昼間人口 by 町丁. The mesh offers the same
2020 residents at *worse* alignment (cells cut through 町丁; representative
points vs cell centroids) and **no daytime at all** — the single field the
whole §2 rule exists for. Strictly worse.

**(c) A Tokyo grid layer (Bangkok has one).** True that Bangkok ships
`districts → station areas → 200 m grid` (`CLAUDE.md:448-451`), but that grid
is built from POI/park/transit rasters, not census mesh; its only
population-ish input is the POI-proxy resident weight (`build.py:947-952`).
Tokyo has no grid level, no level switcher, and the ticket contains no product
ask for one. If the owner ever builds a Tokyo grid, the 500m/125m mesh could
serve as its resident-weight plane (a ~2.5 MB fetch for the bbox, trivial
packing like Bangkok's `uint8 × 250` plane) — but that is a hypothetical
consumer to be researched under that future ticket, not a reason to adopt mesh
into the current pipeline. This is also exactly how Bangkok would consume its
own census data if Thailand published one; nothing Tokyo-specific is gained by
anticipating it.

## 4. Numerical example on real data (one run, in memory)

I reproduced the pipeline's Tokyo neighborhood logic from the repo's own cached
inputs (`.cache/crime/tokyo`, `tokyo_daytime`, `boundaries_13` — SHA-256
verified by the script's own `fetch()`), built the 5,068 Tokyo zones
(join rate 99.4%, daytime coverage 99.9% — matching the script's asserts), and
**first validated the reproduction against the committed output**:

| station | my reproduction | committed `data/crime/station-safety.json` |
|---|---:|---:|
| shinjuku | 48.58 (10 zones, unclamped) | 48.58, neighborhood, 10 zones |
| hibiya | 12.19 (16 zones, unclamped) | 12.19, neighborhood, 16 zones |
| sugamo | 20.95 (13 zones, unclamped) | 20.95, neighborhood, 13 zones |

Then the only change: zones are grouped into the 500m cells (5339) containing
their representative points, and the 800 m catchment is drawn from **cell
centers** instead of zone points (crimes/pop/daytime ride along with their
zone into its cell — the best any mesh pipeline could do, since crime is not
published per mesh):

| station | 町丁 catchment | 500m-mesh catchment | delta |
|---|---|---|---:|
| shinjuku | 10 zones · pop 12,442 · day 252,012 · Σw 1,224 → **48.6** | 6 cells / 7 zones · pop 8,717 · day 177,664 · Σw 1,045 → **58.8** | **+21%** |
| hibiya | 16 zones · pop 1,284 · day 216,450 · Σw 264 → **12.2** | 7 cells / 15 zones · pop 1,802 · day 178,226 · Σw 482 → **27.0** | **+122%** |
| sugamo | 13 zones · pop 47,869 · day 47,369 (resident rule) · Σw 100 → **21.0** | 8 cells / 12 zones · pop 42,817 · day 43,551 · Σw 105 → **24.6** | **+17%** |

Why Hibiya doubles, by name — the mesh disc includes cells containing zones
whose own points sit outside 800 m (crimes ride in with the cell):

- **added by mesh:** 新橋二丁目 (897 m, weighted 230), 銀座八丁目 (864 m, 59),
  霞が関二丁目 (881 m, 10), 八重洲二丁目 (809 m, 10);
- **dropped by mesh:** 銀座五丁目 (25), 銀座六丁目 (18), 銀座七丁目 (28),
  丸の内二丁目 (15), 内幸町二丁目 (4).

And why the denominator would break without TMG daytime: the 町丁 catchment
includes 丸の内二丁目 (**0 residents**, daytime 51,120), 有楽町二丁目
(**1 resident**, 6,007), 霞が関一丁目 (0/24,645) — mesh cells cannot even
express "this place's population is its commuters", and the mesh variant's
denominator above only stays sane because it silently borrows the 町丁 daytime
via the same allocation. The Shinjuku catchment is the mirror image: 歌舞伎町一丁目
has **65 residents**, daytime 10,290 and 412 weighted crimes — a quarter of the
catchment's crime in a unit a 500m cell cannot isolate (its cell would blend
Kabukicho with Nishi-Shinjuku office towers).

Conclusion of the example: at equal radius, the mesh aggregation is strictly
less accurate than the 町丁 aggregation it would have to be built from.

## 5. Recommendation

**Reject the source for this pipeline; close CRTKY-183.** Nothing in the
current Tokyo consumers (a)–(b) improves; consumer (c) does not exist and, if
it ever does, the mesh is a data plane for *that* ticket (with the 125m table
T001225 as the finer option, at the cost of heavier secretization). The honest
one-liner: 町丁 is not a compromise that mesh would fix — it is the native
granularity of both inputs (Keishicho crime, TMG daytime), and the mesh is a
re-aggregation of one of them plus an omission of the other.
