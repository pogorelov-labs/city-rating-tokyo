# Air quality as a new category — seasonal PM2.5, Bangkok (CRTKY-146)

Researched 2026-10-13 by an open-data research agent. Method: live HTTP calls
(curl), the gdcatalog CKAN API, Nominatim geocoding, GitHub repo inspection,
web search. Every number below was read or computed in this session unless
marked otherwise. Sources reachable/unreachable from **this network (non-TH
IP)** are flagged, because it materially affects what the pipeline can do.

Question from the ticket: inventory Bangkok PM2.5 stations; is density enough
for 50-district interpolation or only a city figure/facts; hit the API once
and attach the response; pick an honest metric; new category vs facts.

---

## TL;DR

- **Air4Thai webV2 history API works live, no registration, JSON**, hourly
  PM2.5 per station with a per-range summary block — **but it keeps only a
  rolling window of roughly the last 2.5–3 months** (Jul 2026 already gone,
  Aug 2026 present on Oct 13). A burn-season (Dec–Mar) metric must be
  accumulated during the season or taken from the annual CSV archive.
- **Bangkok city has 10 PCD monitors in 9 of 50 districts** (+11 in the metro
  ring → 21 BMR). Median distance from a district centroid to the nearest
  monitor is 4.0 km, mean 6.1 km, **max 28.2 km (Nong Chok)**; 20 of 50
  districts are ≥ 5 km away. Monitors cluster in the core; the farthest
  districts are the outer ones. **District-level interpolation would be a
  distance-decay artifact, not data.**
- **Recommendation: not a new rated category.** A city-level seasonal fact
  ("burn season" chip, season mean / % days ≥ 37.5 µg/m³, live "now" value)
  on all pages, optionally enriched per district where a monitor actually is.
- `pcd.gdcatalog.go.th` (the annual CSV archive, 2011–2025, license "Open
  Data Common") **times out from this network** — catalog metadata verified,
  file contents not. Owner needs to recheck from a TH network/VPN.
- `envilink.go.th` is behind a Cloudflare challenge → **reject** for the
  pipeline. The codeforthailand wrapper is **archived** (moved to databuri);
  OpenAQ normalizes the same monitors but needs a free API key.

## 1. Air4Thai (PCD) live API — verified working

**Endpoints (all hit live on 2026-10-13, no registration, no key):**

| Endpoint | Purpose | Status |
|---|---|---|
| `https://air4thai.pcd.go.th/webV2/history/api/data.php?stationID=…&param=…&type=hr&sdate=YYYY-MM-DD&edate=…&stime=00&etime=24&format=json` | hourly history, multi-station | **HTTP 200, works** |
| `https://air4thai.pcd.go.th/webV2/history/api/station.php` | all-station list (105 nationwide) | **HTTP 200, 56 KB** |
| `https://air4thai.pcd.go.th/forapp/getAQI_JSON.php?…` | old app API | **HTTP 404** (dead) |

**Attached response** (asked-for "hit it once"; compact real excerpt,
station `02t`, 3 hours, as returned — note `format=xml` is accepted but the
body is still JSON):

```json
{"result":"OK","error":"","stations":[{"stationID":"02t","params":["PM25"],
"data":[{"DATETIMEDATA":"2026-10-11 00:00:00","PM25":12},
{"DATETIMEDATA":"2026-10-11 01:00:00","PM25":12},
{"DATETIMEDATA":"2026-10-11 02:00:00","PM25":11}],
"summary":{"PM25":{"max":12,"min":11,"average":11.67,"totalcount":3,"count":3,"countPercentage":100}}}]}
```

A 12-day pull (2026-10-01→12, `02t`) returned 287 hourly records, e.g.
`2026-10-01 21:00 → PM25:30`, summary `max 32 / average 13.31 / 97.96 %`.
Multi-station and multi-parameter work in one call:
`stationID=02t,03t,05t,…`, `param=PM25,PM10,O3,NO2,SO2,CO,TEMP,RH,WS,WD`
(station `50t` on 2026-10-10 returned PM25 = 23 with values and
TEMP 27.4 / RH 79 / WS 0, while PM10/O3/NO2/SO2/CO were `null` — not every
station runs every analyser).

**Critical limitation — rolling window, not an archive.** Summary counts for
station `02t`, `param=PM25`, 3-day slices (run 2026-10-13):

| sdate | non-null hours | note |
|---|---|---|
| 2025-03-01 | 0 | burn season gone |
| 2026-01-01→31 | 0 (all 10 BKK stations, 744-hr months) | burn season gone |
| 2026-06-01 / 07-01 | 0 | > 3 months back gone |
| 2026-08-01 | 72/72, avg 10.5 | window begins ≈ here |
| 2026-09-01 | 72/72, avg 15.0 | |
| 2026-10-01→12 | 287/288, avg 13.31 | |

So anything longer than ~2.5–3 months must come from elsewhere (annual CSVs
or OpenAQ), or be accumulated by our own cron during the season.

**Data quality note:** single stations drop out for stretches — `03t` was
100 % null in the 10-station Oct 11–12 query yet has 82.7 % completeness over
Aug 1–Oct 12 (1450/1753 hrs); `05t` had 99.4 % over the same window. Per-
station per-period completeness checks are mandatory before averaging.

The `codeforthailand/datasource-air4thai` wrapper (README it in the ticket)
is **archived — "Moved to github.com/codeforthailand/databuri"** (14 ★, last
push 2023). Its `databuri/datasources/air4thai.py` confirms the endpoint
shape used above. Do not depend on it; two curl lines replace it.

## 4. OpenAQ — normalized fallback, needs a key

`GET https://api.openaq.org/v3/locations?coordinates=100.5018,13.7563&radius=10000`
→ **HTTP 401** `"Unauthorized. A valid API key must be provided in the
X-API-Key header."` (live). Key registration is free via explore.openaq.org.
Web search confirms Air4Thai is an ingested provider — e.g.
explore.openaq.org/locations/2326 "Thai Meteorological Department … Provider,
Air4Thai … Reporting since 30/01/2016" and "Bang Phlat District Office,
Bangkok" monitor pages. OpenAQ archives history and normalizes units, but it
mirrors the **same PCD monitors**, so it does not fix the density problem —
it is the backup for (a) historical burn-season data if gdcatalog stays
unreachable, (b) a uniform query layer. It may also lag station renames
(its location names reference older BMA sites).

## 6. Density vs the 50-district frame — computed

Distance from each district centroid (`app/src/data/bangkok/districts.json`,
50 records with lat/lng) to the nearest monitor (haversine, script run this
session):

- districts hosting a monitor: **9 / 50**
- nearest-monitor distance: **median 4.0 km, mean 6.1 km**
- **≥ 5 km from any monitor: 20 / 50 districts**; within 5 km: 30
- worst: **Nong Chok 28.2, Lat Krabang 20.5, Khlong Sam Wa 18.4, Thawi
  Watthana 14.7, Don Mueang 14.1, Sai Mai 13.9, Min Buri 13.3 km**; best
  (host districts) 0.9–1.7 km

Implications:

1. **Interpolation (IDW/kriging) to 50 districts is not defensible.** 40 %
   of districts would get values extrapolated from ≥ 5 km away, and the two
   inner-district monitors are ~2 km apart while outer districts have none
   within 9–28 km. Urban PM2.5 gradients follow roads/industry, not
   distance-to-monitor; the percentile machinery (which ranks districts)
   would rank interpolation error.
2. A **city-level figure** (mean of reporting stations) is honest — on
   episode days the city reads nearly uniform; between episodes it varies by
   district in ways we cannot measure.
3. Station-area / grid levels: even less coverage — one monitor per ~10
   station areas. Facts only.

## 7. What metric is honest

Standards (verified via search: Thailand adopted WHO IT-3 in 2022–23;
Archer et al. 2024; EANET country profile; AirGradient comparison):
**24-h PM2.5 = 37.5 µg/m³, annual = 15 µg/m³** (previously 50 / 25). WHO
final guideline: 5 / 15.

- **Annual mean — rejects itself**: Bangkok annual values sit near the
  standard while the story lives in the season; it also needs a full year of
  per-day data we cannot yet pull from the live API.
- **% of season days with 24-h mean ≥ 37.5 µg/m³ (Dec–Mar)** — the
  communicable, decision-relevant number ("N of 120 burn-season days above
  the Thai standard"); computable from the gdcatalog archive or from a
  season we accumulate ourselves.
- **Season (Dec–Mar) mean at stations** — good secondary, smoother.
- **Live "now" chip** — hourly API supports it natively (`summary.average`
  over the last 24 h per station), one HTTP call per refresh.

Only values I measured this session (Oct, wet season, low): `02t` Oct 1–12
avg 13.3 µg/m³, max 32; Aug avg 10.5. **No burn-season number is asserted
from this session** — the 2025/2026 season data was not reachable
(gdcatalog host timeout, API window). The published PCD/IQAir seasonal
pattern (Dec–Mar highs) is context, not a measurement here.

## 8. Composition options

| Option | Verdict |
|---|---|
| **A. New rated category** (11th, percentile across 50 districts) | **Reject.** 9/50 measured; percentiles would compare measurement vs interpolation; fails the repo's own honesty bar (cf. `00-overview.md` honesty notes). |
| **B. City-level seasonal fact + live chip** on `/bangkok` and every district page ("burn season: Dec–Mar; last season X days ≥ 37.5 µg/m³; now N µg/m³ — citywide, 10 PCD monitors") | **Recommend.** One defensible number, seasonal framing is what actually drives relocation decisions, cheap (one API call), honest about granularity. |
| **C. B + per-district enrichment where a monitor exists** (9 districts: "monitor in this district: latest/season values"; metro-ring context for edge districts) | Optional add-on later; only if the owner wants the extra copy + i18n strings. |

If (and only if) the season is accumulated from Dec 2026 via cron, B can show
a real current-season counter; until then the chip must quote the last full
season from the archive (needs gdcatalog reachability or an OpenAQ key).
